# TTS Player — сессии внутри плеера: свой хвост, синтез только активной. План реализации

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers-extended-cc:subagent-driven-development (recommended) or superpowers-extended-cc:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** у каждой сессии из списка свои сообщения и свой хвост; в демон уходят задачи только
активной сессии (и только пока не звучит свой текст); сообщения неактивной собирают текст и
озвучиваются, когда до них дошло воспроизведение; переключение, очистка и завершение сессии.

**Architecture:** порядок задач демона (`_sequence`, `_task_order`, `_delivered` в
`MessageQueue`) выносится в общий для всех сессий объект — демон синтезирует задачи всех сессий
по одной. Сообщения сессии — своя `MessageQueue` над этим общим порядком; плеер держит очереди
по `session_id` и играет очередь активной сессии — остальная логика курсора (`_start`,
`_message_end`, переозвучка) не меняется. Предложение (13) и склейка истории находят свою очередь
по id задачи и по сессии. Сообщение, текст которого ещё не отдан демону («отложено»), озвучивается
путём переозвучки при начале проигрывания — и по команде, и при автопереходе. Окно пока
показывает очередь активной сессии в прежнем списке; список сессий и кнопки — следующий срез.

**Tech Stack:** Python 3.12 + системный PyGObject — как в `master`. Новых зависимостей нет.

**Slice:** вход плеера «сессии» (`Player.add_session`/`remove_session`/`select_session`/`clear`,
`PlayerState.sessions`/`active`) — внутренний стык между командой сессии (14), задачами хука (11)
и окном. Четвёртым: стоит на влитых (14), (15) и переключённом гейте; окно строится на нём.

**Next slices (not planned here):** окно — список сессий между рядом служебных кнопок и списком
сообщений, клик по сессии, мусорка — «Очистить» активной, [stop] — «Завершить» активную.

**Spec:** `docs/superpowers/specs/2026-10-09-tts-player-sessions-design.md`

**Assumptions:**
- Демон говорит очередь по одному сообщению в порядке поступления (факт спеки), поэтому порядок
  задач — общий для сессий; `is_complete` на нём уже держится (`queue.py`) — не риск.
- Сессия задачи хука — `session_id` задачи = UUID (`CLAUDE_TTS_SESSION` гейта, прошлый срез);
  имя файла демона `tts_queue_<session_id>_…` — та же строка — проверено по `inbox.py` NAME_PATTERN.
- Переозвучка при начале проигрывания (`Player._revoice_if_stale`) уже работает — приём не новый.

## Global Constraints

- Синтезируется только активная сессия: задача хука уходит в демон (12), только если её сессия
  активна и свой текст не звучит (`hold`); иначе — только текст в хвост своей сессии.
- Хвост — на каждую сессию отдельно, размер из настроек плеера (`Prefs.tail`).
- Задача хука сессии не из списка — удалена со строкой в журнале; перед разбором задачи хука
  плеер забирает лежащие в `control/` запросы (`ControlRequests.drain`).
- Порядок задач демона общий для всех сессий.
- Клик по другой сессии: звук стоп, она активна, её текущее — первое непрослушанное, статус
  stopped (ждёт play/pause); клик по активной и по неизвестной — ничего.
- «Очистить» (`clear`) — сообщения активной сессии (тексты и звук) удалены, сессия остаётся.
  «Завершить» (`remove_session`) — сессия из списка, её тексты и файлы удалены сразу; была
  активной — активной нет, пока пользователь не выберет сессию.
- Первая сессия в пустом списке активна (это делает `Sessions`).
- Сообщения переживают перезапуск плеера в своих сессиях; сообщения сессий не из списка при
  старте не восстанавливаются.
- Тесты не трогают настоящий `$XDG_RUNTIME_DIR` и `~/.claude-tts`.
- Коммит по путям, без `Co-Authored-By`; без `git push`.

**User decisions (already made):**
- Синтезируется только активная сессия; неактивная собирает текст, звук — когда сессия стала
  активной и до сообщения дошло воспроизведение, тем же путём, что переозвучка.
- Хвост на каждую сессию; список главного экрана — сообщения активной; клик по сессии
  переключает и список, и плеер.
- Свой текст забирает канал озвучки; сессии в это время записывают свой текст в память.
- Завершена активная — активной не становится никакая, пока пользователь не кликнет.

### Task 1: Очередь сессии над общим порядком задач

**Goal:** несколько `MessageQueue` делят один порядок задач демона: предложение задачи одной
сессии завершает более раннее сообщение другой.

**Files:**
- Modify: `tts_player/queue.py`
- Test: `tests/test_queue.py`

**Contract:** внутренний интерфейс очереди, которым пользуется плеер

```
class TaskOrder:
    """Порядок постановки задач демону для всех сессий; наибольший доставленный."""
    def link(self, task_id: str) -> None              # следующий номер
    def order(self, task_id: str) -> int
    def deliver(self, task_id: str) -> None           # пришло предложение задачи
    def delivered_after(self, task_id: str) -> bool   # доставлена задача, поставленная позже
    def snapshot(self, task_ids: Iterable[str]) -> tuple[dict[str, int], int]   # (task_order, delivered)
    def restore(self, task_order: dict[str, int], delivered: int) -> None

class MessageQueue:
    def __init__(self, tail: int, order: TaskOrder) -> None
    def owns(self, task_id: str) -> bool               # задача — одного из его сообщений
    # остальное — как сейчас; QueueSnapshot прежний (task_order, delivered берутся из TaskOrder)
```

**Acceptance Criteria:**
- [ ] две очереди с общим `TaskOrder`: задача `a` (очередь A) поставлена раньше `b` (очередь B); предложение `b` пришло → сообщение A `is_complete`
- [ ] предложение `a` не завершает сообщение B, поставленное позже
- [ ] `owns` отвечает по id задач живых сообщений; после `clear()` — `False`
- [ ] `restore` снимков двух очередей поднимает общий порядок: новая задача после restore — позже всех восстановленных и доставленных
- [ ] прежние тесты `tests/test_queue.py` зелёные (с одной очередью поведение не изменилось)

**Verify:** `python3 -m unittest tests.test_queue -v` → `OK`

**Steps:**

- [ ] **Step 1: Failing acceptance** — две очереди, общий порядок, критерий 1. Падает: `TaskOrder` нет.
- [ ] **Step 2: Вынести порядок** — логику `link`/`is_complete`/`release`/`restore`, касающуюся порядка, перевести на `TaskOrder`; `MessageQueue` без `order` не строится (плеер и тесты передают свой).
- [ ] **Step 3: Verify** — команда выше, затем весь набор `python3 -m unittest discover -s tests`.
- [ ] **Step 4: Commit** — `tts_player/queue.py tests/test_queue.py` (и тесты, где строится `MessageQueue`, если поменялась сигнатура).

### Task 2: Плеер держит очереди по сессиям и синтезирует только активную

**Goal:** задача хука попадает в хвост своей сессии; в демон — только задача активной при
молчащем своём тексте; отложенное сообщение озвучивается при начале проигрывания, в том числе
автопереходом; переключение, очистка и завершение сессии; сообщения переживают перезапуск.

**Files:**
- Modify: `tts_player/player.py`, `tts_player/model.py`, `tts_player/saved_messages.py`
- Test: `tests/test_player.py`, `tests/test_saved_messages.py`

**Contract:** вход плеера «сессии», которым пользуются команда сессии (14) и окно

```
class Message:
    deferred: bool = False     # текст ещё не отдан демону: сессия была неактивна или звучал свой текст

@dataclass(frozen=True)
class PlayerState:
    …                          # прежние поля — по очереди активной сессии
    sessions: list[Session]    # порядок списка (Sessions.sessions)
    active: str | None

class Player:
    def add_session(self, session_id: str, cwd: str) -> None
        # Sessions.add; у новой — пустая очередь; стала активной (первая) — её очередь играет
    def remove_session(self, session_id: str) -> None
        # Sessions.remove; файлы и тексты сессии удалены; была активной — звук стоп,
        # активной нет: current None, status idle, messages []
    def select_session(self, session_id: str) -> None
        # активная или не из списка — ничего; иначе звук стоп, Sessions.active = она,
        # current = первое непрослушанное её (нет — None), позиция 0,
        # status stopped (с current) / idle (без), сообщение не начато
    def clear(self) -> None
        # очистка буфера активной сессии: звук стоп, её файлы и тексты удалены; сессия остаётся

messages.json: у сообщения ключ "deferred" (bool); нет ключа — false
журнал: «session select <uuid>», «task <id> <session> deferred», «task <id> <session> dropped: not in list»
```

**Acceptance Criteria:**
- [ ] задача хука сессии `A` (активна) → в очереди демона одна задача, сообщение в `state().messages`
- [ ] задача хука сессии `B` (в списке, неактивна) → в демон ничего; сообщение `deferred` в очереди `B`; в `state().messages` (активная `A`) его нет
- [ ] задача хука сессии не из списка → в демон ничего, нигде нет сообщения, строка журнала «dropped»
- [ ] задача активной, пока звучит свой текст (`hold`) → `deferred`, в демон ничего
- [ ] лежащий в `control/` запрос `add B` до задачи хука `B` → задача принята (не «dropped»)
- [ ] `select_session("B")` при игравшей `A` → звук стоп, `state().active == "B"`, `current` — первое непрослушанное `B`, статус stopped; play/pause → текст отложенного уходит в демон (переозвучка), сообщение играет по мере прихода предложений
- [ ] автопереход к отложенному сообщению активной сессии (автовоспроизведение включено) отправляет его текст в демон и ждёт предложения — не пропускает его как прослушанное
- [ ] `select_session` активной или неизвестной сессии — состояние не меняется
- [ ] хвост на сессию: при `tail=1` начатое сообщение сессии `B` не вытесняет начатое сообщение сессии `A`
- [ ] предложение задачи сессии `A`, пришедшее после переключения на `B`, попадает в сообщение `A` и не играет
- [ ] `clear()` — удалены файлы и сообщения только активной сессии; сообщения `B` целы
- [ ] `remove_session` неактивной — её файлы удалены, активная играет дальше; активной — звук стоп, `active None`, `messages == []`; поздние предложения удалённой сессии удаляются как чужие
- [ ] выход и старт плеера: сообщения `A` и `B` восстановлены в своих сессиях, `deferred` сохранён; сообщения сессии, которой нет в `sessions.json`, не восстановлены (их файлы удалены)
- [ ] `tests.test_player` прежних случаев зелёный: `PlayerCase` регистрирует в `setUp` сессию `S` (активной), в которую идут их задачи

**Verify:** `python3 -m unittest tests.test_player tests.test_saved_messages -v` → `OK`

**Steps:**

- [ ] **Step 1: Регистрация в тестах** — `PlayerCase.setUp` добавляет сессию `S` через `add_session` до задач хука; прежний набор остаётся зелёным на текущем коде (сессия пока ни на что не влияет).
- [ ] **Step 2: Failing acceptance** — задача неактивной сессии `B` не уходит в демон. Падает: сейчас уходит.
- [ ] **Step 3: Очереди по сессиям** — `Player` держит `dict[session_id, MessageQueue]` над одним `TaskOrder`; играет очередь `Sessions.active` (нет активной — пустая очередь без сообщений); предложения — в очередь, которая `owns` их задачу; склейка — в очередь `entry.session_id`.
- [ ] **Step 4: Отложенные** — `deferred` у задачи неактивной сессии и при `hold`; начало проигрывания (`_start`) отложенного — отправка текста (12) тем же путём, что переозвучка, без условия `requested`; `deferred` снимается при отправке.
- [ ] **Step 5: Сессии** — `add_session`/`remove_session`/`select_session`/`clear` по контракту; `_on_hook_task` сначала `drain()` запросов `control/`.
- [ ] **Step 6: Перезапуск** — `messages.json` с `deferred`; восстановление — по очередям сессий из `Sessions` (загружен до `player.start()`), прочее не восстанавливается.
- [ ] **Step 7: Остальные критерии** — тест на критерий, каждый сначала красный.
- [ ] **Step 8: Verify** — команда выше, затем весь набор.
- [ ] **Step 9: Commit** — изменённые пути по именам.
