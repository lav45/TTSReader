# TTS Player — текст сообщений и кэш озвучки

**Статус:** реализовано 2026-10-09 — контракты (11)–(13) в master, переход на живой установке выполнен; проверено пользователем 2026-10-09, закрыта.

## Задача

Плеер хранит текст сообщений и сам озвучивает его через демон. Озвученные файлы — кэш.
Смена голоса или скорости делает кэш невалидным: текст нужно озвучить заново.

## Решения

Со слов пользователя, 2026-10-09:
- Плеер сохраняет текст и озвучивает его через демон.
- Озвученные файлы сохраняются как кэш.
- При смене голоса или скорости кэш невалиден, текст озвучивается заново.
- Хранится и переозвучивается текст обоих видов: сообщения главного экрана (ответы Claude) и
  свой текст экрана «Свой текст» (2026-10-09).
- Переозвучка — очередью демона, буквально: плеер кладёт задачу в `~/.claude-tts/queue/`
  (2026-10-09, против моей рекомендации «процессом синтеза среза (10)»).
- В `~/.claude-tts/queue/` задачи кладёт только наш плеер; демон полностью под управлением
  плеера (2026-10-09). Следствие: хуки Claude Code больше не пишут в очередь сами — текст
  ответа должен попасть сначала в плеер.
- Текст ответа попадает в плеер так: гейт запускает `claude-tts speak --from-hook` с HOME,
  подменённым на каталог плеера; хук пишет готовую задачу в «почтовый ящик» плеера, плеер
  сохраняет текст и перекладывает задачу в настоящую очередь демона; heartbeat в подменённом
  каталоге ведёт плеер (2026-10-09, моя рекомендация, принята; проверяется пробой).
- Переозвучка — при проигрывании: сообщение с устаревшим кэшем помечается в списке; когда до
  него доходит воспроизведение или клик + play, плеер отправляет его текст в демон и играет по
  мере синтеза (2026-10-09, моя рекомендация, принята).
- Текст и кэш — временные, как сейчас (`$XDG_RUNTIME_DIR`): после перезагрузки история
  пуста (2026-10-09, против моей рекомендации «текст постоянно, кэш временно»).

Факты (проверено 2026-10-09):
- `~/.claude-tts/handy_analysis.db`, таблица `speech_history`: на каждое сообщение — `file_name`,
  `created_at`, `session_id`, `project`, `persona`, `text`, `speed`, `tone`,
  `duration_seconds`. Плеер уже читает её (`tts_player/history.py`) ради склейки, но без `text`,
  `persona`, `speed`.
- Очередь демона — `~/.claude-tts/queue/<ts>_<id>.json` (`audio.py:660–690`: `text`, `persona`,
  `speed`, `session_id`, `project`, …). Хук пишет в неё только при живом демоне.
- Звук демона идёт через обёртку `paplay` в буфер главного экрана — сообщение, озвученное
  повторно через демон, придёт туда как новое, если его не пометить.
- Проба 2026-10-09: `claude-tts speak --from-hook --hook-type stop` с HOME=<каталог>, где лежат
  копии `config.json` и `sessions.d/` и свежий `daemon.heartbeat`, пишет задачу в
  `<каталог>/.claude-tts/queue/` (отфильтрованный текст, `persona`, `speed`, `voice_sherpa`,
  `speaker_sherpa`, `session_id`); настоящая очередь не тронута. Сессия берётся из
  `transcript_path` (`/projects/<проект>/`). Хук пишет в `<каталог>/.claude-tts/`: `debug.log`,
  `active/`, `queue/`; водяной знак «уже сказано» — в `/tmp/claude_tts_spoken_<uuid>.state`
  (не зависит от HOME).
- Имя файла предложения от демона — `tts_queue_<session_id>_<token>_s<N>.wav`, где `token` —
  случайный на каждый проход синтеза (`daemon.py:692`, `secrets.token_hex(3)`), а не id
  сообщения; плеер сейчас группирует предложения по `(session_id, token)`
  (`tts_player/inbox.py:17`). id задачи (`daemon.py:1014`, 16 hex) в имени файла нет — его
  приносит (13).
- Синтез в файл в обход очереди — `daemon_generate_speech` (срез (10), процесс синтеза
  `tts_player/synth_worker.py`).

Конец сообщения по числу предложений (2026-10-10, по замечанию пользователя «не изобретать
велосипед», вариант A принят):
- Демон делит текст задачи `claude_code_tts.bridge.split_sentences` и знает число предложений n
  (`daemon.py:805`, журнал «sentence i/n»); текст у плеера тот же — задача уходит демону как есть.
  Плеер считает n той же функцией из окружения claude-tts (как `synth_worker` для своего текста),
  постоянным процессом-счётчиком, один раз на сообщение при задаче хука.
- Сообщение завершено, когда у его последней задачи пришли предложения со всеми индексами
  0…n−1 (любого прохода); прежние признаки (склейка, запись истории, предложение следующей
  задачи, не отдано демону) остаются запасными — счётчик недоступен, демон сбился.
- Склейка остаётся для бесшовного звука; угадывание конца по ней и по порядку событий больше не
  главное. Правка «забрать `inbox/` перед склейкой» отброшена.

## Цепочка

Согласована 2026-10-09.

```
Stop/PostToolUse-хук Claude Code → tts-gate.sh
  └─ claude-tts speak --from-hook  с HOME=$XDG_RUNTIME_DIR/tts-player/hook-home
       │ (11) задача хука в hook-home/.claude-tts/queue/
       ▼
TTS Player: хранит текст сообщения; решает — новое сообщение или переозвучка устаревшего кэша
       │ (12) задача демону в ~/.claude-tts/queue/ — пишет только плеер
       ▼
демон claude-tts → paplay = обёртка daemon-bin/paplay
       │ (13) файл в inbox/ с id задачи из ~/.claude-tts/playback.json
       ▼
плеер: id задачи → сообщение → кэш → игра
```

Кэш сообщения невалиден, если его `persona` или `speed` не совпадают с текущими (активная
персона и её `speed` в `~/.claude-tts/config.json`).

## Контракты

Нумерация продолжает спеки плеера и экрана настроек ((1)–(10)).

### (11) Хук → плеер: задача хука

Пишущая сторона — `claude-tts speak --from-hook` (не меняется), запущенный гейтом с подменённым
HOME; читающая — плеер.

```
hook-home = $XDG_RUNTIME_DIR/tts-player/hook-home        создаёт и чистит плеер при старте
  .claude-tts/config.json   → символьная ссылка на ~/.claude-tts/config.json
  .claude-tts/sessions.d    → символьная ссылка на ~/.claude-tts/sessions.d
  .claude-tts/daemon.heartbeat   пишет плеер: unix-время, раз в 10 с, пока жив настоящий демон
                                 (свежий ~/.claude-tts/daemon.heartbeat ≤ 30 с или живой PID
                                 из ~/.claude-tts/daemon.pid); демон не жив → файл удаляется
  .claude-tts/queue/<ts>_<id>.json   пишет хук (сначала .tmp, затем rename)
HOME=<hook-home> ставят сами скрипты speak-response.sh и speak-intermediate.sh (их зовут и
                  гейт, и tts-command.sh при /tts-on); voice-context.sh — без подмены (уточнено при
                  планировании (12) — моё решение)
задача (формат claude-tts 9.20.1, audio.py:670):
  {"id","timestamp","session_id","project","text","persona","speed","speed_method",
   "voice_kokoro","voice_kokoro_blend","voice_sherpa","speaker_sherpa","voice_mlx",
   "speaker_mlx","lang_mlx","pitch_filter"}
плеер: забирает *.json (не *.tmp) по порядку имени, сохраняет сообщение (текст и поля задачи),
       удаляет файл; не JSON / нет text → файл удалён, строка в stderr
```

### (12) Плеер → демон: задача демону

```
~/.claude-tts/queue/<time:.6f>_<id>.json     пишет только плеер; .tmp + rename
поля — как в (11); id — новый id плеера (16 hex); timestamp — время записи;
"source": "tts-player" — обязательно: демон пишет id в current_message только для задач с
source (`daemon.py:1447, 1499–1501`); цена — демон заводит запись в JOBS, а `/stop` моста
с этим source отменил бы задачу (мост выключен)
новое сообщение: поля задачи хука как есть, id заменён
переозвучка: text сообщения; persona = active_persona; speed, speed_method и voice_*/speaker_*
             — из этой персоны в config.json; session_id и project — сообщения
одна задача на сообщение за раз; ответ демона — файлы по (13)
```

### (13) Обёртка paplay → плеер: файл с id задачи

```
daemon-bin/paplay <опции> <wav>
  id = current_message.id из ~/.claude-tts/playback.json; нет файла / поля / не JSON → "unknown"
  (поле id есть только у задач с source — до (12) задачи хука source не несут, и id всегда
  "unknown"; найдено ревью 2026-10-09)
  inbox/<recv_ns>_<id>_<basename(wav)>       атомарно: .<имя>.part, затем mv (как сейчас)
  сбой → stderr и logger -t tts-player-paplay (как сейчас)
плеер: id → сообщение, для которого задача поставлена; "unknown" или чужой id →
       файл удалён, строка в stderr
```

## Открытые вопросы

- После (13) два прохода одной задачи — одно сообщение (раньше по решению среза (2) спеки
  плеера — два). Пауза демона посреди сообщения: проход 1 обрывается на предложении i без
  записи истории, проход 2 начинает с того же i (`daemon.py:851–866, 1334`), склейка содержит
  только проход 2 (`daemon.py:831`) — длины не сходятся, сообщение играется по предложениям
  и заканчивается без склейки (`ended`). Предложение i звучит дважды (оба прохода) — убирать
  ли дубль по индексу (поздний проход побеждает).
  Решено 2026-10-10 (рекомендация, принята пользователем): дубль индекса той же задачи убирается —
  остаётся предложение позднего прохода (больший recv_ns), если прежнее ещё не звучало; звучавшее
  (играющее и до него) не заменяется, пришедшее удаляется (`MessageQueue.add`, `sounded`).

- Склейка: демон по-прежнему пишет цельный файл сообщения и строку в `speech_history`; связь
  строки с id задачи не проверена — нужна ли склейка, если плеер знает границы сообщения по id.
- Срез «сессии» (черновик `2026-10-09-tts-player-sessions-design.md`) строится на том же входе:
  сессия задачи хука известна плееру (11).
